# Tenant-isolation rollout

Finding: [195c07be](https://helix.pingcap.net/me/github/code-security/findings/195c07be-376d-4f88-9481-c8cff1f26334).

This change binds queued work to its persisted owner and payload manifest. It
does not change database schema, infrastructure, APP_PEPPER, or the plaintext
memory-report credential format. Credential encryption is a separate finding.
Existing memory-report schema initialization remains unchanged.

## Two releases, with separate merges

The production workflow deploys the current `main` commit and updates both API
and worker. It cannot deploy an arbitrary intermediate commit. Do not merge both
phases before completing the first release and its queue reconciliation.

1. **Producer preparation** (`feat/security-tenant-producer`): API adds the
   authenticated `apiKeyFingerprintHex` to batch and deep-report messages.
   Contracts temporarily make this field optional for the old consumers. Worker
   runtime behavior is unchanged. Merge and deploy this phase first.
2. **Worker enforcement** (`feat/security-tenant-isolation`): make the field
   required and enforce ownership, payload manifests, and owner-scoped memory
   report writes. Merge and deploy only after the phase-one checks below pass.

Both branches start from the deployed RE2 release, `b93b953`. Keep that fix and
its long-content compatibility checks in both releases. This document is a plan;
local tests or a green CI run do not establish that either release is deployed.

## Phase-one checks

- Record release commits, image digests, task-definition revisions, and the
  current API/worker pair before deploying. Verify all API tasks now run the
  producer-preparation release; an old API can enqueue work after its HTTP
  response while source preparation finishes.
- Exercise both batch upload and deep-report creation with synthetic staging
  data. Confirm messages contain the owner derived from authentication even if
  a caller supplies a different owner in the request. Confirm the old worker
  can still consume those messages.
- Reconcile old-format batch and deep-report messages in both primary queues and
  DLQs, including invisible/in-flight, delayed, and replay copies. A single zero
  visible-message count is insufficient. Do not print memory-report API keys
  while inspecting messages. Replay or quarantine only reconciled messages; do
  not purge queues or invent missing ownership from an untrusted message.
- Hold phase two if old producers or unresolved legacy messages remain. The new
  worker intentionally rejects missing or malformed owner fields. Other old
  message types retain their existing format.

## Phase-two staging acceptance

Use two dedicated synthetic tenants, A and B, with a ledger of created resource
IDs. Snapshot their report/job state before testing. Do not use customer content
or real credentials in adversarial fixtures.

1. Complete a valid batch, deep report, and memory report for each tenant.
2. Deliver A's owner with B's job/report ID. Verify rejection before S3/source
   reads, model calls, or report/job failure writes; B's state must be unchanged.
3. Substitute another batch's object key, hash, index, or count. Verify rejection
   before S3 access. Verify stored payload metadata and content hash still match
   the database manifest for valid work.
4. For a memory report, mismatch the raw key, owner, report ID, and date range
   individually. Confirm no result or failure is written to the other owner.
5. Exercise duplicate delivery, including one delivery waiting until another
   releases the batch lock. Completed batches must not be counted twice. A
   cancellation or manifest change before lock acquisition must be respected.
6. Inject source/storage failures after a valid owner check. Only that validated
   owner's job/report may receive failure bookkeeping. Completed memory reports
   must not be regenerated by replay.
7. Confirm long-content regression tests still pass. Reconcile only the synthetic
   resources/messages in the ledger, inspect queue/DLQ outcomes, and preserve
   explicit evidence of cleanup; do not delete unrelated messages or resources.

Repository suites cover these boundaries with mocked dependencies and local HTTP
integration. They do not prove real IAM, MySQL, S3, SQS, or mixed-version staging
behavior; record that acceptance separately before a production rollout.

## Rollback

Once enforcement is deployed, retain at least the producer-preparation API as
the rollback baseline. An older API emits messages the enforcing worker rejects.
Rolling the worker back to phase one restores compatibility but also restores the
known missing checks, so it is an explicit incident decision, not an automatic
response to rejected malicious messages. Record a mutually compatible API/worker
pair and reconcile queued work before changing versions. No database rollback or
APP_PEPPER rotation is part of this change.

Do not declare the finding fixed from producer preparation alone. Full
enforcement, staging acceptance, production rollout, and Helix verification are
separate milestones. Any Helix write requires review of its exact text first.
